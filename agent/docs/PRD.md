# Dangoo 艺术创作 Agent 画布改造 PRD

版本：v0.2 · 核心完整性修订稿（替代 v0.1）  
日期：2026-09-16  
适用基线：Dangoo `main@d5e72ad1d10e9d7345d0805d3018de4c8001398a`

## 1. 产品决策

在现有 Dangoo 画布上增加一个能理解素材、操作节点、执行生成任务并持续修改作品的 Agent。用户可以直接说需求，也可以选中节点或资产后继续对话；Agent 的动作和结果都落在现有画布上，用户随时可以手动接管。

采用**基于 Codex 可复用源码复制、提取或改写的独立完整 Agent 内核**。完整保留 runtime、Tool Registry/调用调度、Skill Registry、可替换 Provider、Context Management/Compact、会话持久化与恢复等能力。产品定位为节点画布里的艺术创作 Agent，核心实现的可靠性和完整性不能因“轻量化”而降低。

代码来源可以是 Codex；产品独立构建、配置、认证、调用模型和恢复会话，不要求安装外部 Codex CLI、运行其 App Server，或使用 Codex 账号与服务。复制的源码成为本项目维护的内核组件。

推荐组成是：**现有 React 前端 + 独立 Agent 项目/服务及自有会话存储 + Dangoo 业务接口 + 可替换的推理 provider**。画布、资产文件、钱包仍由现有 PocketBase 所在的业务系统管理；Agent 数据与迁移独立维护。媒体生成先复用现有 RunningHub 能力；Agent 推理 provider 与媒体生成 provider 分开配置。核心语言以源码复用和长期维护成本决定：能独立提取的 Rust 实现允许直接保留，跨语言更合适的模块按行为契约改写。当前 TS 前端不构成“所有核心必须重写为 TypeScript”的理由。Agent 独立开发、测试、构建和版本发布；Dangoo 通过少量接入代码使用它，避免原项目频繁迭代引起核心代码反复合并。部署优先合并同类职责，进程数量不作为削减核心能力的依据。

本版纠正 v0.1 的三个限制：不再预先排除 Codex 核心源码复用；Skill 从简易 loader 提升为完整 Registry；取消未经验证的固定工具总数、两个 Skill、32k 上下文和十二轮模型请求等内核上限。效率通过按需加载、增量上下文、缓存和正确调度获得。

本次交付为需求与方案。本文的“现状”来自源码检查；“要求”“目标”“建议值”描述待实现行为。尚未安装 Dangoo 依赖、启动产品、验证上游模型或执行真实付费任务。本文编写过程未使用 Skill；产品仍按用户要求保留 Skill 能力。

## 2. 现有项目分析

### 2.1 已有能力及其价值

| 模块 | 当前代码事实 | 改造判断 |
| --- | --- | --- |
| 页面 | 首页、`/canvas/:id` 画布、`/admin` 后台；React 19、Vite、Tailwind、Radix | 沿用页面与组件体系 |
| 画布 | 14 种 `CardKind`；节点、连线、分组、视口、图片局部编辑；自定义 DOM/SVG 舞台 | 沿用渲染与手势，不更换画布引擎 |
| 性能 | 几何注册表、拖动直接写 transform、视口相关渲染等优化已存在 | 对话流不得使整张画布逐 token 重渲染 |
| 节点执行 | 参数构造、参考图解析、费用确认、并发池、轮询、结果回写大量位于 `useCanvas.ts` | 从 React 生命周期中提取命令与任务执行 |
| Agent 节点 | 从上游文本和图片构造一次 LLM 请求，输出文本或 JSON 表格 | 作为“文本处理节点”继续存在；新增的全局 Agent 负责连续工具调用 |
| Loop 节点 | 从 Agent 节点文本/表格拆分任务，一次最多 20 条 | 复用已有批次语义，不增加第二套工作流编排器 |
| LLM | 当前 hook 调用 `/v1/chat/completions`，显式 `stream: false`；前端失败时轮询结果 | 不具备所需的流式 tool loop；新增推理适配层 |
| 保存 | 整体 `CanvasDoc`、`canvas_rev`、保存幂等键、本地 IndexedDB、冲突恢复 | 保留恢复能力，统一结构化写入入口 |
| 资产 | 全局 `assets` 记录；项目资产存在 `CanvasDoc.projectAssets`；底层文件在 `media_files` | 统一读取与引用，区分资产、集合与物理文件 |
| 生成结果 | 先显示上游 URL，再异步转存；节点包含 `results[]`、`taskId`、`refUrls` | 生成产物应自动登记为资产，URL 仅为访问方式 |
| 钱包 | 已有费用预估、生成扣费、冻结/冲销相关逻辑和充值后台 | 复用计费入口；Agent 不能自行计算或直接改余额 |
| 平台集成 | VibeX 子路径、登录头、RunningHub 中转、桌面助手 | 当前产品接入保持可用，不作为新 Agent 内核依赖 |

关键源码定位见第 16 节。`src` 与 PocketBase hooks 的 TS/TSX/JS/CSS 合计约 4.19 万行，其中 `useCanvas.ts` 8,883 行。这个数字说明改造应围绕现有职责提取，避免把新循环继续塞进同一个 Hook。

### 2.2 当前方案的主要断点

1. **动作与页面耦合。** `handleRunGenerateNode → runBatchNodes → launchSpecs → runJob` 依赖 `setCards`、refs、toast、登录弹窗和浏览器 AbortSignal。直接把这些函数暴露给模型，关闭页面后任务跟进与结果入库仍不可靠。
2. **同一份数据可能被多方覆盖。** 现有 `PATCH /api/canvases/{id}` 收整份文档，执行读版本、比较、保存。该路由没有显示出把读版本与写入包在一起的事务/CAS；不能据此认定它已经支持手动操作与 Agent 并发写入。
3. **资产有多个身份。** 全局资产 ID、项目资产 ID、节点 ID、文件 URL 分别存在；图片组用 URL 成员，工作流结构复用 `images` 字段。Agent 缺少稳定的检索、查看、引用契约。
4. **任务恢复依赖页面。** 已有 `pendingJobs`、远端任务 ID 和恢复轮询，但尚不能替代服务端持久任务记录。新 Agent 必须知道“提交成功”“生成完成”“文件已保存”“已应用到画布”分别发生了什么。
5. **当前 UI 位置会冲突。** 资产面板位于右侧，底部还有节点编辑与生成浮条。新增悬浮聊天框需要面板避让、焦点和事件隔离规则。
6. **运行基线仍需补证据。** 本地 `vite.local.config.ts` 的 `/__pb` 代理未移除前缀，主配置有该处理；本地脚本与 PocketBase hooks 目录的实际加载也需要启动检查。以上是实施前的定点检查，不是已经确认产品无法运行。

### 2.3 最重要的改造顺序

先建立 Codex 核心复用清单与行为验收基线，同时确定资产身份和统一节点命令，再把完整内核接入画布，最后让聊天 UI 消费同一事件流。复用工作按职责切开，不以一个简易 tool loop 代替全部内核。

## 3. 目标用户、场景与范围

### 3.1 用户目标

- 创作者：把“找素材、写提示词、搭节点、生成、比较、继续修改”串成连续操作。
- 熟悉画布的用户：选定节点后让 Agent 批量改参数、补全连线、生成多个版本，再继续手动编辑。
- 不熟悉模型参数的用户：表达成品目标，由 Agent 查询可用节点和模型能力，选择合法参数并解释需要的输入。

### 3.2 核心验收场景

| 场景 | 用户输入示例 | 期望结果 |
| --- | --- | --- |
| 从素材开始 | “用这张产品图做三张干净的白底主图” | 锁定选中图片身份；查看图片；创建/配置生成节点；确认必要费用后生成；三项结果可定位与继续引用 |
| 改已有画布 | “把选中的两个节点改成竖版，保留主体，重新生成” | 只修改明确选中的节点；保留输入快照和旧结果；新结果逐项回到对应节点 |
| 找历史素材 | “找一下这个画布上次生成的第二张图，沿用它的背景” | 检索上次批次的稳定顺序，必要时回看图片；下游收到相同资产 ID 对应的图片 |
| 跨回合继续 | “还是用刚才那张，把颜色改淡一些” | 压缩或刷新后仍能解析“刚才那张”，确认素材失效时明确提示 |
| 批量工作 | “给这五张图都做一个 5 秒视频” | 形成有数量、输入和费用范围的批次；限制并发；每项状态独立；部分失败可单独处理 |
| 整理画布 | “把这一组按生成顺序排好，标题改成春季方案” | 一次结构化命令完成排布与命名，不需要调用图像模型 |

### 3.2.1 艺术创作的工作方式

Agent 围绕“理解创作意图 → 建立或调整节点 → 使用真实参考素材 → 生成候选 → 观察结果 → 对照要求继续修改”的循环工作。用户可以直接执行，也可以先讨论方向；明确的简单任务不强制展示计划。

创作上下文应持续保存主体、风格、构图、色彩、材质、光线、比例、局部范围、不可改变的特征、已选版本和用户反馈。能够回答“这次改了哪里、沿用了哪张参考图、哪些要求仍未满足”。

多轮创作允许保留候选并作比较，优先在既有节点结果或相邻候选中组织，不覆盖用户选中的版本。Agent 可基于视觉检查指出差异；审美偏好与用户验收不能由它自行宣告完成。自动继续生成受已授权目标和费用范围约束，不能以“继续优化”为由无限收费。

工具、Skill 和 Context 的领域适配承载这些创作语义；runtime 继续保持可组合、可恢复的执行内核。未来增加新的艺术媒介主要扩展工具与资产能力，避免再次重写核心循环。

### 3.3 首版边界

首版完整能力包括：持续多回合 runtime、完整工具注册与调用、Skill Registry、Provider 注册与替换、上下文管理与压缩、会话恢复、资产理解、现有节点操作及浮动流式对话。当前产品以一个主 Agent 服务用户；内核的工具扩展和调度接口按完整契约建设，不为当前界面形态写死。

采用单画布会话。一个画布可保存多个对话，但同一画布同时仅允许一个 Agent 写入任务；手动操作可继续，冲突按第 7 节处理。账户级资产在授权范围内可读，其他画布的结构修改需要进入对应画布发起任务。

下列能力不进入首版：多 Agent 调度、通用终端/代码执行、浏览器自动化、插件市场、任意 MCP 连接、跨项目长期记忆、定时自动工作、向量数据库、独立工作流设计器、全套 Codex 客户端或权限 UI。已有桌面助手保留现有用户操作，首版 Agent 不自动驱动本机软件。

## 4. 核心复用架构与 Provider

### 4.1 源码复用决策

| 方式 | 本项目采用原则 | 验收要求 |
| --- | --- | --- |
| 直接复制/提取 Codex 模块 | 模块边界清楚、依赖能在本产品中闭合时优先采用；允许保留 Rust 实现 | 独立构建与运行；相关行为测试通过；无隐含 Codex 账号/服务依赖 |
| 复制后适配 | 原实现可用，但模型协议、存储、认证、指令或工具默认集与 Dangoo 不同 | 保留原机制，替换注入点；明确适配前后行为差异 |
| 按源码与测试改写 | 跨语言或依赖耦合使直接复制不合算时采用；TS 是候选实现语言 | 先定义行为契约，移植相关测试，证明核心能力没有被缩减 |
| 调用外部 Codex CLI/App Server | 会形成用户不接受的产品运行依赖 | 不采用；可以复制适合的协议/事件设计到自主代码 |

选择依据是能力完整性、可验证性与维护成本。源码文件不等于可独立复用模块；先追踪依赖闭包，再确定每个模块的直接复制或改写范围。当前 PRD 不虚构已经完成这一提取或移植。

```text
React 画布 + 悬浮对话
        │ 发消息 / 手动命令 / 接收事件
        ▼
独立 Agent 内核（复用、适配或改写 Codex 核心）
  Session / Turn Runtime ── Provider Registry / Adapter ── 推理模型 API
  Tool Registry / Scheduler ── 画布节点与资产工具
  Skill Registry ── 创作方法、参考资源、工具依赖
  Context Manager / Compact ── 历史、创作约束、资产引用、状态增量
  Durable Events / Recovery ── Agent 自有存储、任务跟进与恢复
        │
        ▼
业务适配：现有 PocketBase / 钱包 / 媒体生成入口 ── RunningHub
```

前端不持有推理密钥。业务适配层注入经过验证的身份、画布与授权范围；模型不能指定 owner 或扩大权限。后台 job 具备限定范围的执行身份，不能依赖浏览器 token 永不过期。内核与自有存储、Dangoo 业务接口之间保持明确边界，避免把前端 React 状态或艺术创作字段散落进通用循环。

### 4.2 必须完整保留的核心能力

| 核心模块 | 完整性要求 | 画布场景适配 |
| --- | --- | --- |
| Session / Turn Runtime | 生命周期、同会话顺序、用户补充、持续执行、取消传播、状态机、故障恢复 | 一项创作目标可跨多个工具往返与长时间生成继续完成 |
| Tool Registry / Router | 名称/命名空间、版本化 schema、能力发现、参数校验、结果多模态、错误语义、调用关联 | 节点、素材、媒体处理成为有类型的工具，不把权限交给模型 |
| Tool Scheduler | 依赖与并行安全、写入互斥、异步等待、幂等、超时、取消收尾、状态事件 | 多张图可并行生成；同一节点写入串行；任务完成可唤醒 Agent |
| Skill Registry | 注册/发现、元数据、作用域、启停、依赖、版本快照、缓存失效、显式/隐式调用、资源读取 | 创作 Skill 可组合、可更新、可追踪；不退化为三段固定 prompt |
| Provider Registry / Adapter | 注册与配置、模型能力、认证边界、原生流、工具往返、多模态、用量、错误/重试、版本与替换 | 推理 provider 可换，媒体 provider 独立；业务代码不理解厂商协议 |
| Context Manager | 历史记录、类型化消息、tool call/result 配对、增量状态、token 预算、相关内容加载、回读 | 记住参考图身份、构图/风格约束、所选版本、局部修改范围 |
| Context Compact | 自动与手动压缩、回合前/回合中安全边界、摘要版本、重注入、失败回退、恢复 | 长期迭代不丢图、不混版本、不重做已经完成的生成 |
| Durable State / Events | 事件关联、checkpoint、重建、重连回放、去重、未决调用核对 | 关闭页面、网络断开或服务重启后续做，避免重复收费 |
| Execution Policy / Hooks | 工具前后校验、授权与预算、受控扩展点、取消传播、记录和错误分类 | 接入账户权限、版本锁、生成报价和产物入库规则 |

这些模块可以复用、提取、改写，但每项行为都必须保留且可验证。实现阶段的切片只影响迁移顺序，不把未迁移项从“完整核心”验收中移除。

### 4.3 provider 契约

内部定义 provider 无关的 `Message / ContentPart / ToolCall / ToolResult / Usage / FinishReason`。Adapter 负责映射请求、解析原生流、处理工具调用 ID、图片传入形式、结束原因与可重试错误。

必须支持：文本流、原生结构化工具调用、多轮工具结果回传、取消推理请求。完整视觉体验还需要图片输入；视觉不可用时必须标识能力限制，不能声称看过图片。

provider 配置包括：协议类型、服务地址、服务端密钥引用、模型、上下文上限、输出上限、能力标记、超时及并发限制。**只替换 base URL 不视为适配完成。** 不以文本解析“模拟工具调用”，不把 JSON-only 能力当成 function calling 已通过。

首版先实现拟接入 provider 对应的一种协议；若它支持 OpenAI-compatible Chat Completions，可以先实现该 Adapter。只有第二家实际使用不同协议时才增加另一个 Adapter，不预建多厂商框架。实施阶段已指定 GLM-5.3-Flash，使用独立 OpenAI-compatible Adapter；2026-09-16 已完成真实流式工具调用和本地画布节点往返验证，视觉输入与账户限额仍待专项验证。

可替换性要求：业务工具、资产模型、前端事件协议不含 provider 专有字段；provider 原始响应仅作为受控诊断信息。任务恢复使用本产品的消息、摘要与工具记录，不依赖 provider 会话 ID、加密上下文或远端 compact 接口。切换 provider 发生在回合边界；运行中的任务先结束或显式停止，不静默改路由。

实施时用协议样例验证分段工具参数、多工具回传、视觉输入、流中断和 usage 缺失等情况。发布前选定基准与替代两个真实 provider，优先使用同一协议以控制实现范围，运行相同验收任务。协议样例测试不能替代真实替换验证；未取得第二家可用服务时，该项保持未验收，不宣称已验证可替换。

### 4.3.1 Provider Registry 的完整要求

Registry 管理 providerId、配置版本、协议适配器、模型目录与能力、凭据引用、超时和重试策略。凭据由服务端凭据层提供，不出现在 Skill、工具参数或模型可读上下文中。

- 支持注册、禁用、更新与选择 Provider；对话创建时选定配置版本，每个 turn 记录实际 provider/model/revision。
- 能力描述覆盖文本/图片输入、工具 schema 限制、并行调用、上下文窗口、输出上限、usage、停止原因和可选的 reasoning/缓存/远端压缩。能力未知必须探测或标为未知，不靠模型名字猜测。
- 流解析必须覆盖工具参数分片、一个响应中多个工具、正文与工具并存、工具结果的多模态内容、流中断与取消；完成的工具调用不可因模型重试而重做。
- 保留厂商专有内容的受控扩展区；业务/UI只消费统一语义。只有原 Provider 能解释的状态不得原样转交其他 Provider；切换时由规范历史、摘要和资产重新构建合法输入。
- 认证失败、参数不兼容、限流、瞬时网络故障与内容拒绝分开处理。重试策略区分“尚未产生动作”“已有部分工具动作”“已提交收费任务”。
- fallback 是显式配置的策略，并受用户指定模型、预算和权限约束；不能静默换模型改变创作能力或费用。
- Provider 与 Context、Tool Registry 的组合要有契约测试；不能只测纯文本问答就声明替换完成。

### 4.4 推理与生成分离

- **推理 provider**负责理解、调用工具、生成用户可见说明和压缩摘要。
- **媒体 provider**负责图像、视频、语音等生成，首版沿用当前 RunningHub 路由、模型参数和费用逻辑。
- 当前普通 LLM 节点可先沿用原通道；新 Agent 使用独立可配置通道。两种请求的费用来源在后台区分。
- 推理成本与媒体成本分别记账。provider 不返回实际价格时，记录 token/usage 并显示“费用待核算”，不能显示为零。首版可由运营承担 Agent 推理成本并通过服务端额度限制控制；若需向用户收费，应明确费率后再启用，模型不得自定价格。

### 4.5 独立代码与低侵入接入（本版新增约束）

原项目近期频繁迭代。Agent 采用独立项目和独立 Git 仓库，建议与现有 `dangoo` 同级放置为 `dangoo-agent`；这是实施布局建议，本次仅写 PRD，尚未创建仓库。核心、创作 Skill、Provider、上下文、会话服务、悬浮对话 UI 和接入适配器均在该项目维护。独立仓库不意味着复制原项目的画布业务。

```text
DangooCanvas/
  dangoo/                         原产品持续迭代
    src/integrations/agent/        挂载、上下文桥接、事件接收
    服务端 agent-bridge 接口       业务命令、权限、版本和任务入口
  dangoo-agent/                   独立开发与发布（拟建）
    core/                        Codex 来源的核心与适配代码
    providers/                   Provider 注册与协议适配
    skills/                      创作 Skill 包与注册配置
    adapters/dangoo/              原产品 API 与 Agent 工具之间的转换
    contracts/                   版本化 DTO、事件和兼容性样例
    server/                      API、认证适配、存储、恢复与服务装配
    ui/                          悬浮对话组件和独立状态管理
```

目录可以按最终语言细化；职责归属必须清楚。核心不能 import Dangoo 的 React Hook、页面类型、PB collection 实现或模型常量。`adapters/dangoo` 可以了解 Dangoo 的版本化业务协议，不越过协议直接读写生产库。

#### 4.5.1 数据与代码的归属

| 对象 | 权威维护方 | 集成方式 |
| --- | --- | --- |
| runtime、Skill/Provider/Tool Registry、Context/Compact | Agent 项目 | 自主构建的库/服务；不在原项目复制一份 |
| 聊天 UI、消息 store、流式与恢复逻辑 | Agent 的独立 UI 包 | 原项目固定版本依赖，通过 props/接口挂载；沿用原项目样式 token |
| 选中节点、视口、用户当前画布、未提交手动修改 | Dangoo 前端 | 轻量 HostBridge 提供快照/订阅；发送前确认文档同步状态 |
| 节点种类、参数、连线规则、运行语义、模型目录 | Dangoo 业务层 | 能力目录与类型化命令；Agent 适配器转换，不维护第二套规则 |
| 画布/资产/权限/钱包/媒体 job 的事实 | Dangoo 服务端 | 同一业务命令入口、现有存储和账本；API 返回版本与回执 |
| Agent 会话、工具记录、Skill/Provider 快照、摘要/checkpoint | Agent 服务 | 独立存储与迁移，不向原 PB 塞入全部 Agent 内核表 |
| 远端生成任务跟进 | Agent 跟进层 + Dangoo 任务服务 | Agent 记录关联和等待；真实提交/查询/计费仍经 Dangoo 服务，使用稳定 jobId |

媒体 job 的提交、业务幂等、远端任务 ID、费用和应用回执由 Dangoo 任务服务权威管理；Agent 的认领/租约仅控制状态跟进和推理续跑，不形成第二个收费提交者。重复请求携带相同 operationId，由业务入口返回原回执。

Agent 自有状态默认采用一个独立 SQLite 存储，或复用移植核心中已验证的本地持久化实现；通过存储接口封装，长期需要多实例时再选择共享存储。画布和文件不复制进 Agent 数据库，会话仅存授权引用及必要输入快照。这样保留完整恢复能力，同时隔离数据迁移和发布节奏。

#### 4.5.2 原项目的必要接入点

1. **前端挂载：** 一个 `AgentPanelHost` 挂载独立 UI 包；一个 HostBridge 输出 canvasId、选中对象、内容版本、已保存状态和资产引用，并响应定位/预览动作。聊天 store 与 `useCanvas` 分离。
2. **业务接口：** 增加有版本的能力目录、画布读取/增量命令、资产读取/解析、生成任务和状态接口；业务命令仍由原项目掌握其事务与权限。
3. **身份与配置：** 给 Agent 服务提供限定受众、限定用户/作用域的认证机制；前端只知道接入地址与功能开关。不能把 PB 管理密钥交给模型或浏览器，也不能把登录 token 转发到任意动态地址。
4. **手动与 Agent 共用执行：** 逐类提取节点的纯参数校验和服务端运行接口，手动按钮与 Agent 同时调用。优先增量接入 generate 等节点，不提前全量拆解 8,883 行 Hook，不在 Agent 仓库复制该 Hook。

独立接入仍需要上述小范围原项目改动。只在外部加一个服务，无法自动补上原项目缺失的原子写入、服务端任务运行与结果应用能力；这些业务边界必须真实实现，不能绕过为直接改库或模拟点击。原项目已具备的能力直接适配，缺少的能力按节点逐项补齐。

#### 4.5.3 版本契约与兼容规则

- API 使用明确的 `contractVersion`；能力目录另有 `capabilitiesRevision`。Agent 建连先握手，获取实际支持的节点、操作、参数与状态语义。
- UI 包、Agent 服务与 Dangoo 适配器按版本发布，原项目锁定明确版本；不跟随独立仓库 main 自动更新，也不复制粘贴最新源码进入原项目。
- 允许兼容版本范围内的新增字段/能力；不认识的字段忽略，不认识的节点标记“当前 Agent 暂不支持”，原手动功能照常使用。新模型参数从业务能力目录取得，不能靠 Agent 的过期常量猜测。
- 不兼容变更发布新契约版本，适配器在明确过渡期支持所需旧版本；不建设无限兼容层。原项目变更契约时同步更新样例与契约检查。
- turn 和 job 固定执行快照及能力版本。上游升级后先查询既有 job，不能把新参数用于重发旧收费任务；旧能力被撤销时明确失败或等待处理。
- 写命令前必须看到已同步的内容版本；用户离线未保存时可继续讨论，但针对未同步内容的执行等待同步或显示具体阻塞，不拿旧服务端快照冒充当前画布。

#### 4.5.4 独立开发、测试与故障隔离

Agent 仓库提供独立 UI 预览和 HostBridge/业务 API 的契约样例，使 runtime、Skill、Provider 与对话展示可以在原项目持续更新期间单独开发。样例不能替代真实集成验收；每次候选发布都通过当前受支持的 Dangoo 接口验证。

双方 CI 只需要共享契约测试与一组关键集成场景；内部函数重命名或组件重构不应要求 Agent 同步修改。原项目通过小型功能分支接入；避免长期持有改动大量业务文件的 Agent 集成分支。

Agent 服务失联或 UI 包加载失败时，显示重连/不可用状态，画布手动操作与保存继续工作；未完成 job 可通过业务任务状态查询恢复。关闭接入开关不删除会话、不取消已受理的媒体生成、不改变原产品账本。

## 5. 会话、执行循环与事件

### 5.1 一次请求的生命周期

1. 前端上传附件，取得资产 ID；捕获用户发送时的选中节点/资产、画布 ID 和版本。
2. 服务端验证身份、资产权限和画布版本，创建用户消息及运行记录，返回确认。
3. 组装有限上下文，调用推理 provider，正文增量即时展示。
4. 收到完整工具参数后，校验并执行；流中的半截 JSON 不能触发操作。
5. 把工具的结构化结果回传模型。只读请求可有限并行；同画布写命令串行。
6. 生成工具返回持久 `jobId` 后显示“已提交”。服务端跟进任务，完成后登记资产、应用结果，再恢复 Agent 对结果的处理。
7. 用户目标完成后输出简洁结论及结果入口。只完成提交、只完成部分结果、等待用户或达到预算时，分别显示对应状态。

### 5.2 状态语义

| 对象 | 状态 | 产品含义 |
| --- | --- | --- |
| Run | queued / running / waiting_user / waiting_jobs / compacting / completed / partial / stopped / failed | 对话中的一次用户目标执行 |
| Tool call | pending / running / succeeded / failed / canceled | 一次工具是否成功完成自身职责 |
| Generation job | created / submitting / submitted / running / succeeded / failed / canceled / submission_unknown | 媒体生成状态；响应不明不得推断未提交 |
| 结果入库 | pending / stored / failed | 文件和资产是否已可靠登记 |
| 结果应用 | pending / applied / conflict / target_missing | 是否已经出现在目标节点 |

`node_run` 工具 succeeded 表示成功建立并提交任务，不代表图片生成成功。只有要求的产物已入库且应用完毕，或用户只要求提交时，才能结束为 completed；其他情形保留 partial/waiting 状态。

### 5.3 异步与恢复

- 前端收起面板、切画布或关闭浏览器，服务端任务继续。刷新后读取会话与任务状态；无需重新提交生成。
- 请求发出前，持久化 job、输入快照与幂等键；收到远端任务 ID 后立即写入。请求超时且受理未知时进入 `submission_unknown`，先查询/对账。没有可靠查询或上游幂等能力时，要求用户决定是否承担再次提交的费用风险。
- 重启后恢复未完成 job 的跟进；任务状态核对不调用推理模型。任务有有意义的新结果时才恢复 Agent。
- 首版通过持久任务表 + 单进程定时调度实现。每个任务有租约/认领状态，避免重启或部署短时双进程重复执行；不引入 Redis 队列。
- 同一运行中的多个任务完成事件可以合并一次唤醒。持续轮询由任务调度器执行，模型不反复调用 `job_get` 等待。
- 节点已删除或输入版本已变化，已完成资产仍保留在本画布产出里，不自动覆盖用户的新内容。

### 5.4 停止与补充消息

“停止”终止当前推理和后续工具调度，取消尚未提交的媒体任务。已提交任务仅在媒体 provider 支持时尝试取消；不支持时显示“已停止后续操作，2 个已提交任务仍在运行”。已经完成的画布操作不自动撤销，已发生费用不承诺退回。

用户可在运行时补充要求。补充消息带去重 ID，进入同一会话；在下一安全边界处理。尚未执行的计划按新要求更新，已提交任务使用原始输入快照。若是更换主体、参考图或目标等实质变化，先解释已执行部分，再处理新任务；不能修改一个运行中 job 的参数冒充原任务。

## 6. 节点操作工具化

### 6.1 设计原则

工具直接操作有类型的业务对象。Agent 不模拟鼠标、不依赖 DOM 选择器、不调用 React Hook，也不直接提交整份任意 `CanvasDoc`。

手动操作与 Agent 使用同一命令执行层、参数校验和任务服务。前端负责选择、拖动、预览和交互；后端负责权威文档写入、任务提交、结果入库和计费。拖动过程保留本地即时反馈，松手后提交一次变更。

### 6.2 首批业务工具目录与注册扩展

下面 13 项是首批业务工具，不是 Tool Registry 的能力上限。Registry 支持新增节点/媒介工具、命名空间、版本化 Schema、按需发现和依赖声明。常用工具直接可见，长尾能力通过注册目录查询后加载；选择粒度以模型可靠调用为准，不为压低工具数量塞进无边界的通用执行接口。

| 工具 | 输入重点 | 输出重点 / 约束 |
| --- | --- | --- |
| `canvas_read` | 当前画布、选中/指定节点、是否需要相邻连线 | 版本、节点摘要、引用 ID；默认不返回整份文档 |
| `canvas_apply` | base revision、operations[] | 一次原子变更、受影响节点、版本、可撤销操作 ID |
| `node_catalog` | 节点种类/所需能力 | 可用节点与模型、输入槽位、参数 Schema、限制、费用预估能力 |
| `node_run` | 节点 ID/明确批次、输入版本、批准范围 | job IDs、输入摘要、费用信息；先校验全部目标，部分无效不静默跳过 |
| `job_get` | job IDs | 聚合状态、结果资产、错误与实际费用；查询不产生新任务 |
| `job_cancel` | job IDs | 未提交取消/上游取消结果/无法取消；不等同于退款 |
| `asset_search` | 名称/描述/标签、类型、范围、来源、游标 | 分页目录、稳定顺序、简短摘要；默认当前画布优先 |
| `asset_get` | asset IDs、所需详情 | 元数据、版本、关系、来源；大工作流详情按需读取 |
| `asset_view` | asset IDs、可选裁剪/帧时间 | 真正送入模型的图片内容和引用标签；不是仅返回 URL |
| `asset_manage` | collect / rename / annotate / move，资产 ID | 收藏/命名/元数据/文件夹操作；禁止任意文件或数据库操作 |
| `skill_read` | 已公布的 skill ID、version、可选资源名 | 指定版本正文或包内资源；不接受任意系统路径 |
| `result_read` | 本会话 resultRef、游标、所需字段 | 分页回读被截断的工具结果；重新校验对象权限，不能读取其他会话任意记录 |
| `ask_user` | 简短问题或具体操作预览、可选项 | 用户答案/授权记录；身份和批准凭证由服务端产生 |

`asset_view` 是 Dangoo 的统一命名；FDAgent 的 `view_asset` 仅为参考实现名称，本次不导入其工具注册表，不增加别名兼容层。

`canvas_apply` 的 operation 枚举：create_node、update_node、duplicate_node、delete_node、connect、disconnect、layout、group、ungroup、attach_asset、select_result、instantiate_workflow、undo_operation。每种操作单独有 schema，禁止通用任意字段 patch。单次事务建议最多 20 项，默认全成功或全失败；大操作在已有授权范围内自动拆分、记录进度和依赖，不因此削减整个任务可完成的规模。

工具入参中的 `canvasId`、`nodeId`、`assetId` 即使由模型给出，也必须再次校验所属权限。模型不能传入 owner、账本金额、管理员身份或可信批准状态。

### 6.3 现有节点如何映射

| 现有节点 | 新执行方式 | 必要输入与验收 |
| --- | --- | --- |
| prompt | create/update | 文本写入可读节点；无生成费用 |
| result / video | attach_asset / select_result | 使用已有图片/视频资产，保留来源和结果项身份 |
| generate | node_run | 提示词、明确有序参考图、模型参数；多结果各有 assetId |
| polish | node_run | 文本/图片输入，输出文本并写入指定节点 |
| agent | node_run | 延续文本/表格处理；全局 Agent 不在此递归创建另一套 Agent runtime |
| loop | node_run | 冻结表格行和引用、保留现有 20 条上限；批次与子 job 可单项追踪 |
| camera | create/update/attach | 更新结构化摄影配置，运行时冻结合成提示词 |
| layer | node_run | 源图、分析参数、各图层输出；每个产物有父资产及图层身份 |
| replicate | node_run | 正面/背面/Logo/二维码按槽位引用，保持顺序与展开面关系 |
| merge | node_run | 原图、局部图、选区/遮罩、颜色匹配参数；输出保留完整来源 |
| tts | node_run | 文本、克隆与情绪参考音频；产物进入音频资产类型 |
| motion | node_run | 主体图片与动作视频按角色区分，不能依赖 URL 数组猜角色 |
| vsr | node_run | 原视频、参数与输出视频关系 |

所有节点都进入该映射。实施先打通 generate 的完整闭环，然后迁移其余适配器；尚未迁移的节点在 catalog 中返回明确不可自动执行及原因，不能当作已经支持。

图片裁剪、拼接、图层融合和视频取帧可能依赖浏览器 Canvas/媒体能力。供 Agent 自动执行的部分必须成为服务端可执行适配器或确定性媒体工具；需要用户框选的操作先请求用户提供选区。不能因为浏览器面板收起就让已承诺的自动操作中断。

### 6.4 输入快照与幂等

每次运行保存 `nodeId + nodeVersion + parameters + prompt + orderedAssetRefs + skillVersion + provider/model` 的不可变快照。节点继续被编辑时，已提交任务仍按快照执行。

所有写工具有唯一 operation ID 和参数指纹，同一 ID 同体重试返回原结果，异体重试报冲突。退款、撤销和重跑是独立动作；生成重试不能复用“查询失败”作为新付费请求的理由。

## 7. 画布协作、版本与撤销

内容写入以服务端命令处理为准。新端的手动操作和 Agent 都提交增量命令；旧整文档保存入口仅用于旧版本兼容，仍要求版本校验。兼容入口与新命令入口必须进入同一个原子版本检查/写入机制。

原项目的业务命令服务在 PocketBase 事务或等价的持久 CAS 内完成：读取当前版本 → 验证命令和前置条件 → 应用全部操作 → 增加内容版本 → 写入操作回执。不能只靠 Agent 服务进程内锁保证正确性。

- 平移、缩放、当前选择、面板位置属于用户视图状态，不推进共享内容版本。
- Agent 发送请求时冻结选中 ID；后续手动点击其他节点不改变这次操作对象。
- 内容版本落后时，服务端返回受影响对象。仅对字段互不重叠的操作进行确定性合并，例如用户移动位置、Agent 修改提示词；同字段冲突需要重新读取或用户选择，不自动强制覆盖。
- 修改生成输入后，旧任务产物进入该节点历史结果或待应用区，不能悄悄变成新输入的生成结果。
- “撤销本次画布操作”按 operation 回执恢复结构和参数；只在涉及字段仍与该操作执行后状态一致时直接撤销。否则提示冲突，不回滚整张画布。
- 撤销不撤回已调用的外部模型、不自动删除文件、不退款。删除节点不删除资产原文件。

## 8. 面向 Agent 的资产库

### 8.1 资产身份与范围

建立统一资产目录，以稳定的 `assetId` 标识逻辑资产，以 `(assetId, version)` 唯一定位不可变的内容版本。节点、对话附件、生成结果、图组成员和工作流输入都使用该组合引用。长期关系不存签名 URL；访问和提交任务时才解析可用地址。

沿用已有 `assets` 与 `media_files`，逐步扩展元数据与集合关系；项目库从“画布 JSON 内的完整副本”迁移为资产 ID 列表/成员关系。当前所谓“项目”实际对应一个画布，首版不额外引入大型项目管理层。

范围包括当前画布资产、当前会话引用、本账号全局库。范围由权限与成员关系决定，可一个资产加入多个收藏位置；全局库表示本账号跨画布复用，不表示所有用户公开。

目录权限与文件字节的访问权限分别验证。当前媒体代码以长期可展示链接为目标，增加目录 ACL 不会自动让旧公开链接变为私有。新 Agent 只能通过授权解析服务取得媒体；如产品要求私有素材，文件访问还需受保护下载或限时授权链接，并兼顾浏览器预览和 provider 拉取。历史链接的实际可访问性在迁移前核实，界面不能先行承诺“私密存储”。

### 8.2 最小数据要求

| 字段组 | 必需信息 | 目的 |
| --- | --- | --- |
| 身份 | assetId、version、ownerId、kind、createdAt | 稳定引用与权限 |
| 内容 | 文件引用、MIME、尺寸/时长/大小、thumbnail/preview、storageStatus | 选择合适的输入和预览 |
| 语义 | 名称、简短描述、标签、描述来源与生成时间 | 低成本检索；区别用户标注和模型推断 |
| 来源 | upload / generated / imported / edited，canvasId、nodeId、jobId、turnId | 追踪“哪一次”“哪一张” |
| 关系 | parents[]、variantOf、groupMembers[]、workflow 内容引用 | 保持改图、组图、工作流结构 |
| 顺序 | batchId、outputIndex、role、order | “第二张图”“首帧/尾帧”可确定解析 |
| 状态 | ready / processing / missing / deleted / unsupported | 不把不可用内容交给生成模型 |
| 收藏 | 画布/全局库成员关系、文件夹 | 自动登记与用户收藏分开 |

`version` 是从 1 开始的内容版本号。新上传和每个生成/编辑产物创建新 assetId、version=1；编辑产物通过 parents/variantOf 关联原资产。只有用户明确“替换该资产文件”才在同一 assetId 下增加内容版本，并保留旧版本。重命名、标签和描述变化只更新 metadataRevision，不改变内容版本。引用省略版本时，服务端在发送/提交边界解析当前版本并冻结，之后不得漂移到新版。

权限归属于逻辑资产，旧版本同样受当前权限约束；缓存键含 assetId、内容版本和处理参数。内容 hash 可用于识别重复上传，但不能跨账号合并权限，也不能把“文件相同、语义角色不同”合成一个引用。

### 8.3 三层读取

1. **目录层：** 每轮默认注入选中资产和最近相关资产的简短目录，最多 20 项。包含 ID、名称、类型、尺寸、来源、顺序和一句描述，不包含 base64 或全部历史 URL。
2. **详情层：** `asset_get` 获取需要的属性、关联和工作流信息。大型数据分页/分段返回，结果附游标或可再读的结果引用。
3. **内容层：** `asset_view` 在权限校验后取真实图片，以当前 provider 支持的视觉输入送入模型。返回与图片一一对应的 assetId/版本/角色标签。描述与缩略图元数据不等同于视觉证据。

图组按成员 ID 和稳定顺序展开；工作流展示节点和输入输出摘要，实例化后生成新节点 ID。视频首版支持封面、时长与指定时间帧；音频支持元数据及已有转写。尚未具备视频整体理解或转写能力时，明确显示支持范围，不伪称已完整观看/收听。

### 8.4 从查看到生成必须保持同一引用

工具对外使用统一的 `AssetRef`：`{assetId, version, role, order}`，可附已有 crop/mask/timeRange 描述。生成参数的 `references[]` 使用该结构；服务端重新校验 ACL、解析文件并转换为媒体 provider 所需 URL/文件名。

例如，Agent 回看上一轮的 `asset_a/version_1` 作为主体，选 `asset_b/version_2` 作为背景，则 `node_run` 的两个引用必须包含相同 ID、版本、角色和顺序。不得仅从本轮上传附件重新组装参考图，更不能在解析失败后悄悄变为文生图。

用户说“第二张”时，先按照最近明确讨论的批次或选中图组解析 `outputIndex/order`，不按照 UI 当前排序或数据库返回顺序猜测。存在两个合理批次时，用两张缩略图进行一次简短确认。

### 8.5 生成产物自动进入可读目录

每个生成/编辑结果都自动登记为当前画布的资产，并记录 job、输入和结果顺序；登记不等于加入全局收藏。用户点击“收藏到全局库”才新增全局成员关系。资产面板增加“本画布产出”过滤，避免自动产物淹没用户精心整理的全局库。

生成状态与存储状态分别展示：上游完成但转存失败时，显示“已生成，保存待重试”，保留远端任务 ID 和访问情况。不能把有过期风险的临时链接标为已可靠保存，也不能把丢失的内容当成 ready 引用。

### 8.6 检索与语义补全的轻量策略

首版采用当前画布、来源、类型、文件夹、名称/描述关键词筛选，相关结果再排序。没有有效描述的资产也可按时间、节点或批次找到。按需看图产生的简短描述可缓存；不在导入时对整个资产库自动做收费视觉分析。

用户纠正的名称和标签优先。模型生成描述记录来源和版本，不能修改原文件事实。视频抽帧、图像描述等按 assetId+version+处理参数缓存，只有内容改变才重新执行。

### 8.7 FDAgent 参考原则

采用其“轻量 inventory → 按需 view_asset → asset ID 引用 → 运行前受控解析”的思路，并延续历史参考图和批次顺序的语义。Dangoo 具有跨画布全局库，权限范围需要调整为账号与画布成员关系，不能照搬仅同一 Thread 可读的边界。

具体当前源码证据与可复用边界见第 16 节的 FDAgent 部分。参考行为契约，不整体引入 FDAgent 的服务器、数据库、部署和业务模块。

## 9. Skill Registry、Context Management 与 Compact

### 9.1 完整 Skill Registry

Skill 提供可复用的创作方法、约束、步骤与参考资源；Tool 提供经校验的执行能力。Registry 是独立模块，承担从包发现到执行上下文注入的完整生命周期。首批内置创作 Skill 是内容起点，不是只能支持固定几条 prompt 的实现限制。

| 环节 | 必须具备的行为 |
| --- | --- |
| 注册与发现 | 从批准的内置、用户、画布作用域包发现 Skill；注册/更新/移除有明确结果；坏包隔离并给可理解错误 |
| 元数据与校验 | id、名称、简介、版本/内容 hash、来源、作用域、正文、资源、工具依赖及能力要求；检查缺失与格式错误 |
| 名称与作用域 | 同 ID 多来源有明确优先级（显式版本 > 画布 > 用户 > 内置）；同层冲突报歧义，不随机选择 |
| 启用与可用性 | 可查询/启停；依赖工具或视觉能力不可用时标记原因；禁用不是删除历史版本 |
| 选择与组合 | 用户显式选择、模型基于目录匹配、多个相关 Skill 组合；冲突规则服从用户需求与产品约束 |
| 按需加载 | 简介用于发现，执行前读取所需正文；资源分页/按节读取，不能截去关键规则后当作完整加载 |
| 版本与快照 | turn 固定所用版本与内容 hash；热更新使缓存失效，新 turn 生效；进行中的任务可恢复原快照 |
| 资源与执行 | 包内文档、参考图、模板等通过受限读取器访问；可声明脚本/处理依赖，由已注册且已授权的执行器处理；无执行器时明确不可用 |
| 依赖与预算 | 解析工具依赖与循环依赖，按相关性和上下文预算调度；不设“同时最多两个 Skill”的内核限制 |
| 可观察性 | 记录何时匹配/加载/采用哪个版本及失败原因；前端显示中文创作方法与当前阶段，不倾倒全文 |

首版不建设公共插件市场；仍须能通过服务配置或受控管理入口注册、更新和启停 Skill，并通过完整 Registry 加载，不要求每增加一个 Skill 就改 runtime 源码。`SKILL.md` 等现有格式可直接适配；包路径和资源根属于本产品，不依赖 Codex 本机目录。

Skill 不能提升权限、绕过费用确认或覆盖用户约束。用户提供的参考图片、OCR 和外部文档作为内容读取，不自动成为高优先级指令。已撤销的资产/工具权限即时生效，即便旧 Skill 快照仍可恢复。

首批可提供商品图套图、参考图持续修改、艺术风格探索、图片到短视频等创作方法。应能支持用户显式只讨论、先出多个方向或直接执行，避免所有艺术任务被固定步骤套住。


### 9.2 上下文组成

按稳定顺序组装：产品规则与工具目录 → 当前 Skill → 任务摘要 → 最近完整回合 → 当前用户输入及选中上下文 → 本轮必要的工具结果。实际组装需维持 tool call 与 tool result 的配对关系，不把本轮结果随意插到旧对话之间。

Context Manager 管理完整历史与模型本次可见上下文两个视图。历史记录持久化、可回放；本次上下文依据目标、选中对象、依赖与预算选择内容。`canvas_read` 与资产工具按需补足；每次写入前重新验证事实与版本。

必须支持类型化角色和文本/图片/工具内容、tool call/result 完整配对、正在进行的调用、取消与失败记录、历史版本、状态增量和 token 使用。恢复缺失结果时先核对真实调用状态；确实中止的调用可记录中止结果，不得补造成功。

稳定规则和工具 Schema 保持顺序，画布状态用有版本的增量注入，避免每轮改写全部历史破坏缓存。事实变化、Provider 切换或压缩后的基线失效时重新注入完整必要状态。多模态内容按资产 ID/版本回读；压缩掉图像数据不等于遗失其身份。

### 9.3 完整压缩与恢复

依据实际 Provider/模型上下文窗口、输出预留、多模态估算、工具 Schema 和用户配置动态计算预算；使用实际 usage 校准估算。不设置固定 32k 内核上限。需要控制成本时使用明确的可配置策略，并展示其影响。

支持自动与用户手动压缩；自动触发覆盖回合开始前、长任务中的安全边界、输入/结果过大和实际 context overflow。软阈值应留足一次工具结果与续推理空间，压缩目标随模型与任务调整，不能以机械裁掉最近若干条消息替代压缩。

压缩在完整工具往返后的安全边界执行；未完成的 call/result 对不能拆开。若单个本轮结果超限，先截取摘要并提供结果引用；无法在预算内形成合法请求时进入等待处理状态，不能丢掉用户目标继续猜测。

超大结果以 `resultRef` 存入本会话可回读记录，模型通过 `result_read` 按游标获取需要的片段；摘要保留该引用及结果类型。回读返回的是当时的结果快照，写操作仍需查询当前对象版本。原对象权限撤销或记录过期时明确返回失效，不能回退到未经授权的旧内容。

保留两部分：

- **可读摘要：** 当前目标、用户约束、已作决策、已完成步骤、未完成事项、当前 Skill 步骤。
- **程序维护的事实：** canvas/node/asset IDs 与版本、批次顺序、未完成 job IDs、操作回执、费用批准范围及有效期、当前 provider 配置版本。

程序事实从持久状态读取并核对，不能让摘要模型重新生成 ID、修改批准额度或把失败写成成功。历史消息仍保存在会话记录中，压缩只改变下一次推理所用上下文。

基础压缩通过可替换 Provider 的普通模型请求完成；支持远端 compact 的 Provider 可通过能力接口启用优化，但基础路径必须独立可用。确定性整理负责引用、调用配对和任务事实，不能单独替代创作语义摘要。

压缩结果验证目标/约束、关键 ID、工具配对和待办完整性后，原子写入新摘要/checkpoint，并重注入当前规则、Skill 引用与状态。验证失败回退原上下文或上一个有效 checkpoint，按错误类型有限重试；仍超限才给出可恢复的阻塞。更换 Provider 后重新计算预算与内容形式；不沿用其他 Provider 无法解释的压缩对象。

UI 显示一条轻量状态“正在整理对话上下文”，结束后折叠为时间线条目；不清空用户看到的历史，不把内部摘要全文插成普通聊天消息。

## 10. 悬浮流式对话 UI

### 10.1 入口与布局

画布顶栏增加“Agent”入口；空画布可显示“描述你想做的作品”。选中节点时，工具条提供“交给 Agent”，自动把选中对象加入输入区引用条，不自动发送。

桌面端默认在右下方悬浮：宽 420px，高度 `min(640px, 视口高度 - 104px)`，距右/下边缘 20/24px。按视口自适应尺寸，固定在右侧/右下，不提供标题栏拖动。面板属于屏幕坐标，不随画布缩放。此项按 2026-09-16 实施时用户最新要求修订。

≥1280px 时同时打开资产库和对话，资产库移到左侧 20px；对话留在右侧。较窄视口使用同一浮层内“对话 / 资产”切换，保留对话和输入状态。移动端/窄屏使用底部抽屉作为可用性兜底，本次不扩展为完整移动画布改版。

收起时保留小胶囊：Agent 图标、运行状态、待处理/未读数量。收起不停止执行；点击停止有独立控件。结果到达不强制展开、不抢用户视口。

### 10.3 正文、步骤与结果

- 对话正文不展示 Agent 头像、逐段名称或时间；一轮内连续呈现正文、工具状态和结果，时间仅用于历史会话列表。正文使用真实 provider 增量流，不把完整回复拆字伪装流式。支持基础 Markdown，链接与图片内容经过安全渲染。
- 执行过程展示“正在查看参考图”“已创建节点”“等待生成”等用户可理解的动作摘要。不是原始 JSON，也不展示模型隐藏推理或思维链。
- 每个工具步骤有稳定 ID、状态、简短对象描述和耗时；默认折叠参数，展开可看到与用户相关的输入、模型、数量、费用和错误。内部调用 ID 可在详情复制用于排查。
- 图片/视频/音频结果按批次原始顺序展示。每项支持预览、定位节点、继续修改、收藏。失败项保留位置，可查看原因并按明确费用语义重试。
- 对话中的引用卡与资产面板、画布显示同一缩略图、名称与版本；“正在使用”与“正在查看”是不同状态。
- 最终回复简述实际完成数量、结果位置和未完成项，不重复粘贴所有操作日志。

### 10.4 输入与上下文

输入区支持多行、图片附件、拖入资产、从选中节点添加引用以及 `@` 搜索节点/资产。引用条显示名称、缩略图、来源，可移除；同一文件可按主体/风格等不同角色引用。

发送时冻结附件和选中对象；未上传完成时禁用发送并显示上传进度。点击资产库或对话内部不能清空已加入输入区的引用，需修正当前资产面板点击即清空选中的交互影响。

Enter 发送，Shift+Enter 换行；中文输入法组词期间 Enter 不发送。发送有请求去重 ID，连点、网络重试或重连不产生两条用户任务。

运行时输入框仍可使用。按钮显示“补充”，明确将消息加入当前任务；想开启新目标可在当前任务结束后“新对话”，或显式停止后新建。选择其他画布时切到其对话，不把 A 画布结果显示到 B 画布。

### 10.5 画布联动与面板避让

- 创建节点后短暂高亮；批量新增按相邻区域放置，不覆盖现有节点。点击“定位”才平移/缩放到目标。
- 工具正在修改某节点时显示轻量状态标记，完成后消失；不长期锁住整张画布。
- 聊天文本滚动、选字、拖附件、调整面板大小的 pointer/wheel/keyboard 事件不冒泡到画布手势。
- 输入获得焦点时，空格、Backspace、Delete、复制粘贴等不触发画布快捷操作。Esc 先关闭当前预览/弹出菜单，再收起面板，不暗中取消任务。
- 资产、对话、节点浮条和预览弹窗统一层级；模态确认最高，对话高于普通节点。浮条锚点避开面板遮挡区域。
- 自动滚动只在用户位于对话底部时跟随；用户向上阅读时显示“有新内容”，不拉回底部。

### 10.6 关键状态 UI

| 状态 | 展示与操作 |
| --- | --- |
| 空会话 | 简短说明、2–3 个可直接编辑的任务示例；不展示开发者术语 |
| 等待首个 token | 立即显示“已收到，正在处理”，可停止；不显示虚构进度百分比 |
| 工具运行 | 动作名称、目标缩略图/节点、完成项数量 |
| 等待生成 | “已提交，正在生成”；耗时与并发数量；结果逐项到达 |
| 需要用户信息 | 对话内问题卡，可选项或短文本，保留草稿 |
| 需要费用确认 | 数量、模型/规格、预计费用或上限、已包含操作、确认/取消 |
| 版本冲突 | 受影响节点与具体字段，“使用当前修改重新处理”或明确的恢复选项 |
| 整理上下文 | 单行状态，结束折叠；历史消息保持可见 |
| 连接中断 | “连接中断，正在恢复”；保留已显示内容，禁用不确定的重复提交 |
| 部分失败 | 成功结果继续可用；失败项原因与单项重试入口 |
| 已停止 | 区分已停止推理、取消排队任务、上游仍在执行的任务 |
| 资产缺失 | 缩略图占位、原名称、补充/换图入口；不悄悄换用别的素材 |

采用深色模式，沿用原 Dangoo 深色画布、侧栏、边框和文字层级；Agent 面板使用一致的中性深色基底。延续现有圆角、字体和组件，不建立新设计系统。正文可选中，主要按钮支持键盘焦点，流式区域使用克制的 aria-live，减少动态效果偏好下关闭持续动画。

## 11. 执行权限与费用体验

用户的任务指令覆盖范围内，读取资料、创建节点、配置参数、连接节点等可逆操作直接执行，并提供操作记录和撤销。一般步骤不逐项要求点击批准。

需要确认的情况仅包括：目标或输入存在实质歧义；尚无覆盖本次生成的付费授权；超出已批准数量/费用上限；批量删除或覆盖已有成果等明显破坏性行为。确认展示具体节点、数量、输入和费用，不让用户批准空泛计划。

已有费用授权可以覆盖一个明确批次。授权绑定用户、运行、参数摘要、数量、费用上限与有效期；扩大范围或更换收费参数后重新确认。界面沿用现有费用确认偏好，但额度和权限检查必须由服务端执行。

Agent 不直接操作充值、退款和管理员工具。所有媒体生成仍走当前钱包入口。价格无法可靠估算时明确显示“价格待确认”；按产品已配置策略阻止提交或要求用户作知情选择，不能默认零费用。

## 12. 事件、持久化与接口边界

### 12.1 核心与业务持久对象

Agent 会话数据在独立存储中维护，建议包含下列四类逻辑记录；物理表可适配所复用核心的 schema，不强行压成四张表：

| 对象 | 内容 |
| --- | --- |
| agent_sessions | owner、canvas、当前会话状态、provider 配置引用、当前摘要与版本 |
| agent_events | 用户消息、正文分段、tool 生命周期、确认、任务摘要与终态；包含 turn/run/item/sequence |
| agent_operations | Agent 发起命令的记录、参数指纹、业务回执引用和恢复信息；真实写入幂等与撤销检查由 Dangoo 命令服务持久化执行 |
| agent_jobs | Agent 运行与 Dangoo jobId 的关联、等待/认领/checkpoint；业务输入、远端任务与计费的权威事实通过 Dangoo API 核对 |

资产仍在 Dangoo 业务侧扩展现有集合；收藏成员关系按其查询需要决定。Agent 不直连原产品数据库，所有资产访问经授权接口。核心通过自己的存储接口保留完整历史、版本化配置快照、Skill/工具版本、checkpoint 和操作恢复信息，不能为了限制表数省略。独立数据库可以缓存业务引用快照，但权限与当前版本必须通过原产品接口重新确认。会话事件可以承载消息重建，避免建立内容重复、各自独立更新的聊天数据库。原项目旧 `pendingJobs` 在迁移期间作为业务任务的兼容投影，不作为第二份独立任务真相。Agent 对任务状态的缓存也不能覆盖业务服务的权威回执。

### 12.2 前端事件协议

前端通过 REST 发消息、确认和停止，通过 SSE 订阅状态。持久事件包含 `sessionId/runId/turnId/itemId/sequence/type/timestamp`；工具事件还包含 `toolCallId`，任务事件含 `jobId`。

事件至少包括：message.accepted、assistant.delta、run.updated、tool.started、tool.completed、job.updated、asset.registered、canvas.changed、input.required、context.compacting、context.compacted、run.completed/partial/stopped/failed。

每次运行状态变化都持久化并发送 `run.updated`，包含当前状态、waitingReason、pendingJobIds、pendingInputId、可执行的用户动作及状态版本。首次连接与重连快照返回同一结构；前端不通过最近一条正文或工具事件猜测状态。

主要转移：queued → running；需要回答/授权 → waiting_user；媒体任务未结束 → waiting_jobs；任务成功 → 文件保存 → 资产登记 → 画布应用 → running；有入库/应用失败则保留具体原因并进入 partial 或等待可执行的重试。compact 完成后回到进入前仍有效的状态；停止后到达的结果只更新 job/资产，不重新启动已停止的 Agent。等待与恢复使用同一 runId 和剩余预算。

正文增量按 30–80ms 聚合成段后提交事件，优先落库再发送；sequence 在单会话内单调递增并有唯一约束。重连携带最后已收到 sequence，服务端回放之后的事件；客户端按 ID 去重，不重复追加文字或创建结果卡。较长会话先取分页快照，再接增量。

SSE 心跳可每 15 秒发送一次，不计入业务事件历史。心跳只能证明连接存活；任务状态仍取 job。流结束、浏览器断线和 provider finish reason 都不能单独代表用户任务成功。

### 12.3 身份与内容边界

原产品继续使用 PB 登录体系，通过有限授权的服务接口接入 Agent；两侧逐次验证对象权限。多用户不能共用同一会话上下文或可读资产列表。新服务密钥只在服务端，日志不记录密钥和完整签名链接。

资产名称、OCR、图片文字、工作流注释属于外部内容。它们可以供模型理解作品，不能作为提升权限、调用管理员接口或发送秘密的指令。工具执行层采用白名单和对象级校验，不能依赖提示词自行守规。

## 13. 核心完整性与效率要求

### 13.1 精简外围与消除重复开销

- 完整 Agent 内核与现有业务适配，部署先复用现有存储与任务能力；新增进程/基础设施须解决已确认问题，不为形式拆服务，也不为单进程指标删核心机制。
- 保留完整工具与 Skill 注册能力；实际模型上下文按相关性、能力和预算渐进加载，Schema 与稳定指令保持缓存友好。
- 检索、文件元数据、任务查询、布局、引用解析和常规状态播报使用确定性代码，不额外调用 LLM。
- 图片先用满足理解需求的预览，用户需要细节时再读取高分辨率区域；按资产版本复用视觉输入处理结果。
- 只在依赖允许时并行；同一文档写操作串行。一个批次只估价/确认一次，在批准范围内执行子任务。
- 聊天事件更新独立 store/组件；不把每个 token 写入画布文档或让 `useCanvas` 整体更新。
- 长期日志保留受控字段；巨大工具结果存外部可读记录并返回引用，不无限注入上下文。

### 13.2 资源策略，不以固定小上限定义内核

下列默认值是可调整的调度/显示策略。完整历史、可用工具、Skill 注册量、上下文窗口和持续执行能力不能被它们裁掉。

| 项目 | 初始策略 |
| --- | --- |
| 同会话与画布写入 | 同会话一个活跃执行序列，同画布写入串行；保留排队、补充和恢复能力 |
| 并行工具 | 依据声明的并行安全、依赖和资源类型控制；只读可从 4 并发起步，不写死全局固定值 |
| 媒体生成 | 从 2 并发起步，按 provider 限流、任务规格和授权费用调整 |
| 批量任务 | 现有 Loop 单批 20 项限制可由适配器分批承接；Agent 能在同一授权目标内继续后续批次 |
| 持续执行 | 以目标完成、用户停止、真实阻塞或明确预算为边界；不因固定十二次模型调用就要求用户续点 |
| 预算与失控检测 | 支持 token/费用/时间预算；重复无进展调用、持续相同错误或无结果重试触发恢复/提示；技术硬保护可配置且可恢复 |
| 资产目录与看图 | 目录从 20 条分页开始；视觉按相关性、分辨率与 provider 能力分批，全部资产仍可检索回读 |
| 工具大结果 | 摘要与分页/结果引用；读取能力保留，阈值由内容类型和模型预算决定 |
| Skill | 完整注册与依赖解析；简介索引按预算展示，必要正文/资源逐步加载，不机械限制两个 Skill |
| 压缩 | 实际模型窗口、token 估算和 usage 驱动；回合前与回合中处理，支持手动与失败恢复 |
| 重试与 Provider fallback | 按错误分类、已发生动作及授权执行；付费提交不明先对账；fallback 不改变用户明确模型选择 |

预算跨异步唤醒累计，不能靠不断创建新回合绕过费用限制。范围内尚有可推进工作时自动继续；需要新授权或输入时才等待用户。


### 13.3 可测目标

以声明硬件、浏览器版本、网络和 provider 的测试环境为准。首版建议基准：200 个节点、500 个资产、100 条历史对话。

- 消息接受/本地发送反馈 ≤200ms；服务端接受反馈 p95 ≤500ms，排除公网往返的不稳定部分须单独记录。
- 无 LLM 的结构化查询/命令 p95 ≤300ms；文件处理和大内容读取独立统计。
- runtime 自身在模型往返之间的调度开销 p95 ≤200ms；provider 首 token 和媒体生成耗时单独报告，不作虚假整体时延承诺。
- 流式对话期间拖动画布的 p95 帧时间相对关闭对话基线恶化不超过 20%；验收机上不新增持续超过 100ms 的主线程阻塞。
- 确认网络恢复后 3 秒内恢复可见事件与当前任务状态（测试事件积压规模须报告）。
- 重复消息、重复工具回执、断线回放的验收样例中，重复创建节点、重复提交任务和重复扣费均为 0。
- 记录每任务模型轮次、输入/输出 token、工具调用、生成数量、压缩次数和等待时长；以真实数据决定后续优化，不先承诺内存体积或成本下降比例。

## 14. 实施分段与迁移

| 阶段 | 交付 | 完成判断 |
| --- | --- | --- |
| A：源码复用与完整性基线 | 为 Runtime、Tool/Skill/Provider Registry、Context/Compact、持久恢复逐项冻结复制/适配/改写清单；提取或移植行为测试 | 完整能力表均有实现归属；确认没有把外围剥离变成核心缺失 |
| B：核心移植与业务接入 | 独立仓库构建核心和自有存储；接入目标 Provider、Skill Registry、上下文/压缩及版本化 Dangoo 节点/资产接口 | 无外部 Codex 运行依赖；核心状态、调用、恢复和换 Provider 契约成立；原项目接入改动保持集中 |
| C：艺术创作闭环与 UI | 全部节点适配、视觉资产回读、候选与迭代、费用流程、流式对话与画布联动 | 用户可从意图持续创作并手动接管；长回合不丢参考、约束和状态 |
| D：回归与效率验证 | 源机制行为对照、真实 Provider 替换、Dangoo 契约兼容与独立发布、所有节点及恢复故障样例、性能与灰度 | 第 4.2/9/15 节全部适用能力通过，再报告实际效率与剩余限制 |

实现可先用生成图片做纵向验证，但完整 Registry、Context 与恢复能力从阶段 A 纳入设计和测试。阶段性跑通对话或生成不代表完整核心已交付。



### 14.1 资产迁移

1. 在 Dangoo 业务侧新增资产 schema 和读取适配，保留旧 ID→新 assetId 映射；先能读取旧画布。资产迁移通过该项目的独立 PR 交付，Agent 数据迁移另行版本管理。
2. 已有全局记录保留原记录身份，补充统一字段；项目资产按“owner + canvasId + oldItemId”建立可重复执行的映射。不能只按 URL 合并，因为相同文件可能有不同图组与角色。
3. 为组成员分配独立引用；为工作流建立显式类型与结构引用；原始 `images` 内容在兼容期可读。
4. 将节点 `url/refUrls/results` 解析成新引用，无法解析的标记 missing/legacy，保留旧文本以便追溯。
5. 新生成直接登记统一资产。项目导出带资产映射、关系与实际文件；导入重建本地 ID 并重写所有引用。
6. 校验数量、顺序、成员关系、权限和导出回读后，才让新读取路径成为默认。删除旧数据需另行明确授权；本 PRD 不授权执行迁移或删除。

### 14.2 上线与回退原则

按账号或画布开启 Agent；手动画布仍可用。关闭 Agent 入口后，已提交媒体任务继续完成入库，避免产生付费孤儿任务。会话和操作记录可读，回退前端不能把新引用写坏。代码通过功能分支与 PR 集成，合并与部署分别验证。
